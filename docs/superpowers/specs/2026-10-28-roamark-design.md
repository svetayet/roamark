# roaMark — дизайн-документ

Дата: 2026-10-28 · Статус: согласован с владельцем (устно, всё ниже — решённые вещи, если не помечено иначе)

## Зачем это

Личная библиотека GPX-треков походов и покатушек выходного дня. Главный момент, ради которого всё затевается: **перед выходом с телефона за минуту найти нужный трек и скачать .gpx, чтобы открыть в Organic Maps / maps.me**. Сегодня треки теряются в папках ноутбука и мессенджерах, а карты-навигаторы имеют жёсткие лимиты на количество сохранённых треков.

Владелица одна, пользуется с телефона и ноутбука. В будущем приложение открыто для распространения — по модели «каждый подключает своё хранилище» (см. «Распространение»).

## Цели (v1)

- Загрузка .gpx вручную через кнопку «+»: файл, район, категория (пеший/вело/бег/лыжи), название ≤ 200 симв., описание ≤ 1000 симв. (необязательно). Всё редактируется позже, трек удаляется (с подтверждением).
- Длина трека в км считается автоматически при загрузке из самого GPX.
- Главная: выбор района (выпадающий список, основной — со значком-домиком), список треков района: мини-карточка (карта-миниатюра + название + иконка активности + километраж). Пустой район: «здесь пока ничего нет» + призыв добавить.
- Страница трека: большая интерактивная карта (drag/zoom), название, категория, километраж, описание, кнопка **«Скачать GPX»** — отдаёт **оригинальный файл байт-в-байт**.
- Настройки: тема (светлая / тёмная / как в системе), управление районами: создать, переименовать, назначить основным (ровно один), удалить (непустой нельзя — сначала перенеси треки).
- Район «Рядом» создаётся автоматически при первом запуске, переименовывается, основной по умолчанию.
- PWA: устанавливается иконкой на домашний экран телефона.
- Язык интерфейса: русский.

## Не-цели (v1, осознанно потом)

- Высотный профиль (первый кандидат на v2).
- Спутниковая подложка (лёгкая опция на будущее).
- Поиск/фильтры по названию.
- Оффлайн-режим с кэшем треков.
- Общий инстанс на много пользователей (см. «Распространение»).
- Мультизагрузка треков пачкой: владелица подтвердила, что готова загружать по одному (решено 2026-10-28, вопрос поднимала проверка строителя).
- Расширяемый список категорий — фиксируем четыре.

## Анти-цели (провал, даже если всё работает)

- **Платить за хранение** — чьи-либо треки не должны стоить владелице денег.
- **Мутировать или пересобирать исходные .gpx** — скачивается ровно то, что загружено.
- **Размазать доступ к данным по всему коду** — весь доступ к хранилищу через один тонкий слой (ради переезда на другой бэкенд за дни, не недели).
- Сложный онбординг, требующий карты/оплаты у пользователя.

## Ограничения

- Только бесплатные тарифы: GitHub Pages (фронт), Supabase free (данные).
- Статический хостинг — никакого своего сервера.
- Доступность из РФ: пользователька в России; зарубежная инфраструктура — риск провайдерских блокировок, лечится запасными путями (ниже).
- Основной клиент — браузер телефона (Android/iOS), ширина от ~360 px. Десктоп — тоже работает.
- Сезонность: перерывы до ~2 месяцев зимой (сессия может «засыпать» — уже решено автостуком).

## Решённые решения

### Хранение — Supabase free + GitHub Pages

- **Auth:** вход магической ссылкой на почту, единственный аккаунт — владелица. Публичный сайт без входа показывает только «войдите».
- **Регистрация закрыта (бутстрап «первый — владелец»):** в Supabase остаётся включённой регистрация, но триггер в БД отклоняет любого нового пользователя, если аккаунт-владелец уже существует. Первый зарегистрировавшийся после развёртывания становится владельцем — поэтому в инструкции по настройке шаг «сразу после деплоя зарегистрируйся» обязателен. Это же решение автоматически работает для будущей модели «каждый свой инстанс»: первый пользователь каждого экземпляра — его владелец. Без этого анонимный ключ в публичном бандле позволил бы кому угодно писать в базу за её счёт (нарушение анти-цели).
- **Файлы:** Supabase Storage, bucket `gpx`, путь `{uuid}.gpx` (имя оригинала храним в метаданных, в путь не кладём — юникод/спецсимволы). Скачивание — прямой ссылкой (signed URL для приватного bucket).
- **Метаданные:** Postgres-таблицы (см. «Модель данных»). RLS: все политики через `auth.uid() = user_id` — даже при «одном пользователе» защита на уровне базы.
- **Засыпание:** GitHub Actions в том же репо раз в неделю делает любой запрос к REST API проекта — проект никогда не paupeится и не попадёт под правило удаления 90-дневных спящих проектов. **Уточнение после проверки строителем:** GitHub сам отключает расписанные workflows после 60 дней неактивности репозитория, поэтому тот же еженедельный workflow делает и no-op коммит (обновляет файл-счётчик в служебной ветке), чтобы репозиторий считался активным и расписание не гасло. Остаточный риск (поломка Actions, смена политик) закрывается инструкцией «разбудить вручную»: supabase.com → Restore, пара минут.
- **Распространение (будущее):** код открыт, в настройках/при первом запуске можно указать свой Supabase (URL + anon key) — «каждый приносит своё хранилище». Никто ни за кого не платит; лимиты бесплатного тарифа = естественная квота.

**Запасные пути (не делаем, но архитектура обязана позволять за дни):**
1. Блокировки `*.supabase.co` в РФ → Cloudflare Worker на своём домене как прокси.
2. Полная миграция → Яндекс Облако (Object Storage + Functions + YDB) — по той же причине тонкого слоя данных.

### Карта — Leaflet + растр

- Библиотека: **Leaflet** (растровые тайлы, вес и простота; векторный MapLibre не нужен).
- Основная подложка: **CyclOSM** (`tile-cyclosm.openstreetmap.fr`) — тропы/грунтовки/поверхности выделены.
- В тёмной теме — автоматически **CARTO dark_all** (решение исполнителя по умолчанию, владелица в курсе).
- Обязательная атрибуция внизу карты (Leaflet рисует сам; проверяем, что не отключили).
- Линия трека: изумруд с белой обводкой-кантом (видна на любой подложке), точки старта/финиша.
- Миниатюры в списке: те же тайлы, неинтерактивная Leaflet-карта, `fitBounds` по треку; зум фиксируется (без анимаций), взаимодействие отключено.
- Уважение к тайл-серверам: разумные `maxZoom`, без лишних перезагрузок.

### Данные и правила

- Таблица `districts`: `id uuid`, `user_id`, `name`, `is_primary bool` (ровно один true на пользователя, транзакционно при смене), created_at. Первый запуск: создаётся «Рядом» (is_primary = true).
- Таблица `tracks`: `id uuid`, `user_id`, `district_id fk`, `category enum('hike','bike','run','ski')`, `name varchar(200)`, `description varchar(1000) null`, `distance_km numeric`, `storage_path text`, `original_filename text` (для имени файла при скачивании), `bounds/центр (для мини-карты: `min_lat,min_lon,max_lat,max_lon`), `preview` (упрощённая полилиния ≤400 точек для мини-карт в списке — чтобы список не скачивал файлы целиком; введено при планировании), `gpx_parsed_at`, created_at, updated_at.
- Длина: сумма гаверсинусов по `<trkpt>` (учёт и `<trk>`, и `<rte>`); 3 знака, показ 1 знак после запятой.
- GPX-парсер свой (DOMParser): без внешних зависимостей, он же источник длины и bounds. Битый/не-GPX файл → понятная ошибка, ничего не сохраняется.
- Сортировка списка: новые сверху (created_at desc) — решение исполнителя.
- **Редактирование трека = только метаданные** (район, категория, название, описание). Заменить сам .gpx в v1 нельзя — путь обхода: удалить трек и добавить заново (решение исполнителя; если замена файла важна — сказать при планировании, это отдельная работа в экране редактирования и слое хранения).
- Удаление трека: подтверждение, файл удаляется из Storage вместе с записью.
- Удаление района: запрещено при наличии треков (кнопка неактивна + подсказка «сначала перенесите треки»).

### Технологии (решение исполнителя, владелице безразлично)

- **Vite + React + TypeScript** — быстрый статический билд, экосистема.
- **Supabase JS client** — только внутри одного модуля доступа к данным (`src/data/*`): остальной код не знает про Supabase.
- **Leaflet** через `react-leaflet` или напрямую (на усмотрение).
- **PWA:** manifest + минимальный service worker (app-shell кэш); оффлайн-данные — не v1.
- Деплой: GitHub Actions → GitHub Pages.
- **Разделение труда при запуске (как договорились):** исполнитель готовит всё — код, SQL-миграции, workflow, и **пошаговую инструкцию для владелицы** (создать проект Supabase, прогнать миграцию, создать bucket, вписать секреты в репозиторий, зарегистрироваться владельцем, включить Pages). Владелица выполняет её сама (GitHub она уже знает, Supabase будет новым); если захочет — пройдём шаги вместе в сессии.

## Что осталось строителю

- Структура репозитория и компонентов; именование и разбиение модулей.
- Конкретные экраны и потоки: форма добавления/редактирования, список, страница трека, настройки, экран входа.
- Настройка Supabase-проекта: SQL-миграции (таблицы + RLS + триггер «ровно один основной район»), bucket, ключи в `.env`.
- GitHub Actions: deploy на Pages + еженедельный keep-alive ping.
- Тесты: как минимум — GPX-парсер (валидные/битые/пустые файлы, trk+rte) и расчёт длины; ручная проверка мобильной вёрстки на 360 px.
- Иконки четырёх активностей: единый линейный стиль.
- Проверка палитры на контраст (текст/фон в обеих темах).
