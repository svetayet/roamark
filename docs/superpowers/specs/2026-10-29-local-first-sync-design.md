# roaMark: локальное хранилище + синхронизация с облаком

Дата: 2026-10-29. Статус: ждёт одобрения владелицы.
Предыдущий документ: `2026-10-28-roamark-design.md` (дизайн приложения в целом).

## Зачем

Сети из РФ к Supabase деградированы: мобильный оператор владелицы не пускает supabase.co
вообще, домашний режет скорость; загрузка GPX без VPN не проходит. Приложение при этом
остаётся личной библиотекой треков для одного человека, телефон — основной клиент
(«перед походом открыть и скачать GPX»).

Решение владелицы: **хранить всё локально в браузере**, а в облако синхронизироваться —
«каждая пользовательница указывает своё место». Первый адаптер — **Яндекс.Диск**
(родной для сетей РФ, бесплатные гигабайты, у каждой пользовательницы есть аккаунт),
второй — **GitHub**. Свой серверный код не пишем совсем: браузер разговаривает с API
облака напрямую.

Кнопка синхронизации — **одна**, «синхронизироваться»; конфликты решаются **по датам:
чья запись новее, та и главнее** (решение владелицы; детали слияния — ниже, смягчение
моё: сравнение по-записное, чтобы «новее главнее» не стирало свежее с другого устройства).

## Цели

- Приложение работает мгновенно и полностью без сети: все данные и GPX-файлы — в браузере (IndexedDB).
- Скачивание GPX остаётся байт-в-байт точным (файл хранится как есть).
- Одна кнопка «синхронизироваться»: забрать изменения с облака, слить по датам, выложить итог.
- Яндекс.Диск — первый адаптер, GitHub — второй; дальше любой сможет добавить свой.
- Ноль серверов нашего кода, ноль обязательных платежей.
- Данные в облаке лежат в понятной папке (человек может открыть и увидеть свои файлы).

## Не-цели (первая версия)

- Совместное редактирование несколькими людьми.
- Автоматическая фоновая синхронизация (только по нажатию кнопки).
- Шифрование копии в облаке.
- Supabase-адаптер синхронизации — не делаем. Supabase уходит из проекта **совсем**
  (решение владелицы 2026-10-29): код, миграции, env-сборка, keep-alive workflow и секреты
  GitHub удаляются; сам проект в панели владелица удаляет последним шагом, после проверки
  нового хранилища.
- Красивый OAuth-вход с кнопкой «подключить» (первая версия — вставка токена, см. «Токен»).
- Хранение истории версий в облаке (одна актуальная копия; история — в git приложения и в бэкапах Диска).

## Архитектура

### Локальное хранилище (основа всего)

IndexedDB, база `roamark`, сторе `local` с записями двух видов:
`district` и `track` (ключ — id записи), плюс стор `gpx` (ключ — id трека, значение — Blob
с исходными байтами файла) и стор `meta` (служебное: состояние синхронизации).

`LocalTrackRepository` реализует существующий интерфейс `TrackRepository` (listDistricts,
listTracks, addTrack, deleteTrack, createDistrict, renameDistrict, deleteDistrict,
setPrimaryDistrict, getGpx…). Все операции чтения и записи — локальные и мгновенные.
Каждая запись при создании/изменении получает `updatedAt` (дата по часам устройства).
Удаление — не стирание, а надгробие: запись помечается `deletedAt` (нужно, чтобы удаление
доехало до других устройств; надгробия живут в базе и в манифесте, места занимают копейки).

Приложение стартует сразу в библиотеку: страница входа (magic link) исчезает, демо-режим
исчезает, кэш/повторы главной страницы становятся не нужны (чтение локальное) — их убираем.

### Копия в облаке (формат)

Папка `roaMark` в корне Диска (подтверждено владелицей 2026-10-29):
- `roaMark/manifest.json` — весь каталог: список районов и треков со всеми полями
  (id, название, описание, вид активности, район, километраж, дата создания/изменения,
  originalFilename, bounds, previewSegments, deletedAt для надгробий) + `version` формата
  и `pushedAt` (когда выложено).
- `roaMark/files/<id>.gpx` — сами треки, байты как есть.

### Слияние (правило «новее главнее», по-записно)

Кнопка «синхронизироваться» делает одно и то же всегда:
1. Забрать `manifest.json` с облака (если папки нет — считать пустым облаком).
2. Слить записи попарно по `id`: у каждой записи локальная дата `updatedAt`/`deletedAt`
   и облачная — **побеждает большая дата**. Новые записи с обеих сторон остаются обе.
   Слияние детерминировано: с теми же входами оба устройства получат одинаковый итог.
3. Применить итог к локальной базе.
4. Выложить итоговый манифест и файлы, которых на облаке нет (по `updatedAt` записи и
   наличию файла). GPX-байты перекладываются как есть.
5. Показать сводку: «синхронизировано · забрано N, выложено M · время». Если была запись,
   менявшаяся на обоих устройствах, — отдельной строкой: какая версия осталась и почему.

Удаления: надгробие с датой. Удалила трек на компьютере и синхронизировала — на телефоне
он тоже исчезнет. Удаление против правки — тоже по дате: правка новее — запись воскресает,
удаление новее — остаётся удалённой.

Часы: правило дат опирается на часы устройств; устройства с авто-временем — норма.

### Интерфейс синхронизации в коде

`SyncTarget` — маленький интерфейс, реализации сменные:
- `YandexDiskSyncTarget` (первый): REST `cloud-api.yandex.net/v1/disk/resources`,
  загрузка/скачивание байтов через выданные API ссылки (downloader-домен).
- `GithubSyncTarget` (второй): Contents API приватного репозитория владелицы.
- Общие для обоих: `getManifest()`, `putManifest(json)`, `getFile(id)`, `putFile(id, blob)`,
  `probe()` (проверка «облако на связи» для статуса).

### Настройки: раздел «Синхронизация»

Мокап: `mockups/sync-settings.html` (выбранный вид, палитра «ель», обе темы).

- Пока не настроено: выбор хранилища (Яндекс.Диск ✓ / GitHub «вторым этапом»),
  кнопка «подключить», подпись «что входит в копию».
- Настроено: строка «Яндекс.Диск» + «отключить», статус (✓ всё совпадает · N треков ·
  время последней синхронизации / ⬇⬆ что приедет и уйдёт), **одна кнопка
  «синхронизироваться»**, после нажатия — сводка, при конфликте записи — честная строка
  о том, какая версия осталась.

### Токен

Первая версия — без OAuth-механизма: в настройках поле «вставить токен Яндекса»,
токен хранится в localStorage устройства, вставляется один раз на устройство.
Я дам владелице пошаговую инструкцию, где взять токен (страница подтверждения Яндекса).
Если выяснится, что токены короткоживущие — добавим обмен на свежий или повторную вставку
(см. «Открытые вопросы»). Красивая кнопка «подключить» с согласием Яндекса — улучшение
после первой рабочей версии, если политика Яндекса это разрешает.

## Что уже проверено, что проверить до кода

Проверено сегодня (не из РФ, но это свойства серверов):
- `cloud-api.yandex.net` отвечает на CORS-запросы с адреса приложения (`Access-Control-Allow-Origin`
  прямо для `svetayet.github.io`) — браузер может ходить в API напрямую.
- `api.github.com` отдаёт `Access-Control-Allow-Origin: *`.

Открытые проверки — **шлюзы перед основным кодом** (spike, ~10 минут):
1. **Домен байтов Яндекса**: настоящая загрузка и скачивание файла через выданные API
   ссылки (downloader-домен) из браузера. Если CORS не пустит — порядок адаптеров
   меняется: GitHub первым, Яндекс вторым (или Яндекс только для манифеста — решать по
   результату spike).
2. ~~**Сеть владелицы с мобильного**~~ — проверено владелицей 2026-10-29: с мобильного
   оператора открываются и `cloud-api.yandex.net` (401 + JSON), и `api.github.com`,
   фон-карта в приложении рисуется нормально.
3. **Живучесть токена**: сколько живёт выданный токен, нужен ли обмен.

## Этапность

- **Этап 0 — spike** (после одобрения дизайна): живой тест байтов Яндекса с реальным
  токеном + мобильная проверка владелицы. Решение: порядок адаптеров.
- **Этап 1 — локальное хранилище**: LocalTrackRepository + IndexedDB, приложение уходит
  с Supabase на локальный стор, вход/демо/кэш-с-повторами убираются. Библиотека снова
  мгновенная. (Данные в Supabase у владелицы — только несколько районов, треков ноль:
  переносим руками за две минуты, миграцию не пишем.) Supabase удаляется целиком:
  папка `src/data/supabase`, `supabase/migrations`, env-переменные и секреты GitHub,
  keep-alive workflow. Инструкция владелице: перенести районы → проверить →
  удалить проект в панели Supabase → убрать секреты в настройках репозитория GitHub.
- **Этап 2 — слияние + Яндекс**: даты/надгробия, слияние, одна кнопка, раздел настроек,
  сводка, вставка токена.
- **Этап 3 — GitHub**: второй адаптер через тот же `SyncTarget`, выбор хранилища в настройках.

Внутри этапов — как всегда: проваливающийся тест → код, полный suite зелёный,
`npm run build` перед push.

## Ответы владелицы (2026-10-29)

- Телефон — **Android**: локальная база хранится надёжно, специальных напоминаний
  «синхронизируйся» не делаем (кнопка в настройках и сводка достаточно).
- Папка копии — **`roaMark` в корне Диска**.
- Supabase — **удалить совсем**, без запасного пути (см. «Не-цели» и «Этапность»).

## Решения строителя (проверка документа 2026-10-29, приняты)

- Из `TrackRepository` уходят auth-методы (getSession/sendMagicLink/signOut/onAuth);
  `RepoContext` всегда отдаёт `LocalTrackRepository`; env-переключение на Supabase удаляется.
- Локальное скачивание: `getDownloadUrl` → `URL.createObjectURL(Blob)`. Замечено строителем:
  нынешний демо-репозиторий отдаёт data:-URL — для не-ASCII имён это НЕ байт-в-байт;
  локальная версия обязана идти через blob-адрес.
- Забор GPX-байтов с облака для треков, пришедших при слиянии, — часть шага «применить итог»
  (иначе новый трек останется без файла в оффлайне).
- Сироты: если выживший трек ссылается на удалённый район — район воскресает.
- Инвариант «ровно один основной район»: основной — самый свежий район с isPrimary=true,
  у остальных false.
- Редкий тай-брейк при равных датах: побеждает лексикографически больший канонический JSON
  записи — симметрично на обоих устройствах.
- Надгробие трека при выкладывании удаляет и `files/<id>.gpx` из облака.
- Обрывы: итог применяется к локальной базе до выкладывания; повторное нажатие кнопки даёт
  тот же итог, транзакции не нужны.
- Тесты IndexedDB в jsdom: dev-зависимость `fake-indexeddb`; обёртку над IDB пишем свою
  минимальную (философия проекта — без лишних зависимостей).
- Поле вставки токена не замокаплено — рисуется по палитре и структуре разделов настроек.
- Статус «⬇⬆ что приедет и уйдёт» — dry-run того же алгоритма слияния (забрать манифест,
  слить в памяти, не применять): двух разных логик не делаем.
- Для страницы подтверждения Яндекса нужно одно публичное OAuth-приложение (client_id);
  регистрируется один раз, инструкция владелицы ссылается на него.
- Этап 3 (GitHub): Contents API читает файлы до ~1 МБ, большие GPX — через Git Data API
  (blobs/trees); учесть при планировании этапа 3, этапы 0–2 не блокирует.
- Одновременная синхронизация двух устройств (гонка выкладывания) не защищается —
  пользовательница одна, кнопка ручная. Зафиксировано как граница.

## Ограничения проекта (неизменные)

- Только бесплатное; платное российское — не отменено, но в этом дизайне не нужно.
- Секретные ключи (service_role и т.п.) — никогда в коде и в репозитории; токен Яндекса
  владелица вставляет сама на каждом устройстве, он живёт только в localStorage.
- Весь интерфейс — по-русски, обращение на «ты», женский род.
- Главный сценарий: телефон перед походом, скачать GPX байт-в-байт под исходным именем.
